## Required external handoff before implementation

IS/Nexus must provide an approved, implemented, environment-specific contract for:

1. Resolving the authenticated IS subject to canonical UUID tenant context,
   with current membership and caller-application authorization. Specify response
   fields, UUID validation, errors, scopes, resource/audience and token lifecycle.
2. Selecting a tenant when zero, one or multiple effective tenants exist. There
   is no verified active-tenant contract; Sandcastle must not select the first
   result, derive a tenant from email/domain, or create a default tenant.
3. The exact Sandcastle application/client binding and available entitlement
   semantics. Confirm whether login context resolution requires entitlement;
   no local subscriptions or plan rules will be added.
4. Membership/lifecycle/entitlement revocation semantics, permitted staleness,
   outage behavior and any mandatory per-request validation.
5. Stable subject semantics: existing `user_id` remains the exact IS OIDC `sub`;
   do not rewrite owners to a presumed internal IS user ID. The draft requires
   Identity-owned subject resolution rather than assuming both IDs are equal.

Do not implement the draft as though deployed, forward IS management cookies,
borrow operator credentials, or accept client headers/body identifiers as proof.

## Current context and session implications

Current `AuthenticatedIdentity` and `/api/auth/me` contain only `user_id`, `email`,
`name`. No `tenant_id` enters Sandcastle today. Story queries still require
`Story.user_id == identity.user_id`; another user receives 404.

Sessions are stateless, signed (not encrypted) browser cookies containing those
identity fields. Cookie attributes are HttpOnly, SameSite=Lax, path `/`, and
Secure according to configuration. Both cookie lifetime and server signature
validation use 12 hours. Login flow cookies expire after 10 minutes. IS access
tokens are used during callback and are not retained for later validation.
Protected requests validate the local cookie only; logout deletes that browser's
cookie without server-side revocation. IS membership or identity changes do not
invalidate an already issued Sandcastle session; a copied cookie remains usable
until expiration. This milestone adds no tenant authorization or new stale grant.

Once an upstream contract exists, retain `AuthenticatedIdentity` and add required
`tenant_id` with strict validation at the trusted boundary. Missing/malformed or
unauthorized tenant data must fail before issuing a tenant-bearing session.
Invalidate pre-tenant cookies or require fresh login; never supply a fallback UUID.
Embedding an authorized UUID in the signed cookie is minimal only if the approved
contract permits its staleness. It does not prove continuing membership. The
current draft instead requires live eligibility checks and zero positive
authorization caching, with a <=5-second in-flight decision budget. A 12-hour
membership snapshot would not satisfy it. Determine required server-side token
retention/revalidation from the final contract before choosing an implementation;
do not introduce a distributed session framework speculatively.

## Deferred M11A validation and M11B design

No tenant-aware tests are added against invented fixtures. Once the external
contract is available, mock that exact boundary and test canonical UUID propagation,
missing/malformed/unauthorized context, no/invalid/expired sessions, login/callback
and PKCE regressions, client header/body override attempts, and two different
subjects sharing one tenant while Story access remains user-isolated.

M11B requires separate review. Add `Story.tenant_id` and retain the original owner
as `created_by_user_id`, using canonical IDs and authenticated membership plus
local resource policy. A local projection, if needed for foreign keys, is only a
cache of Nexus identity; no local tenant creation or membership lifecycle.

Use an additive nullable phase, an explicit reviewed owner-to-canonical-tenant
mapping manifest, audited backfill and validation before constraints/access
cutover. Existing users may have zero or multiple tenants, revoked memberships,
or Stories intended for different organizations. Current membership alone is not
proof of historical Story ownership intent. Never infer mappings from email,
domain, matching names, or first membership. Quarantine unresolved Stories and
preserve creator provenance. A shared tenant access cutover can expose formerly
private Stories to other members and needs explicit policy review. Coordinate
Universe/Canon Library and dependent resource boundaries to avoid cross-tenant
links or inherited-data leaks. Preserve original ownership/mapping evidence for
rollback; rollback must not restore centrally revoked access. No M11B work or
migration is included here.
