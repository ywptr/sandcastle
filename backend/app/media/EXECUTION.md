# M4B: approved storyboard execution and artifacts

```text
Sandcastle Story / Canon / Storyboard + user approval
    -> MediaExecutionClient
    -> IG HTTP adapter
    -> IG Control Plane (provider execution)
    -> external image reference
    -> Sandcastle Artifact metadata
```

Sandcastle owns narrative meaning and approval. IG owns provider execution,
job infrastructure, credentials, and media storage. No IG modules are imported,
no IG database tables are shared, and generated bytes do not belong in PostgreSQL.
M3/M4A previews remain ephemeral and make no execution calls.

## Approval and durable state

`MediaExecutionClient` in `execution_client.py` is a narrow synchronous protocol:
`submit`, `get_status`, and `get_result`. The execution service depends only on
that protocol. The API composition injects an adapter; tests inject a fake.
`actor_id` is the requesting IS subject. Caller authentication belongs exclusively
to the adapter and must identify Sandcastle as a service, not impersonate the user.

Approval creates exactly four `MediaExecution` records in one transaction before
any submission. Each stores actor ownership, Story/Scene/plan/request IDs, panel
number, backend name, timestamps, state, external execution reference, diagnostics,
and a JSON snapshot of the exact approved MediaRequest. A digest identifies the
approved plan. Snapshots are application-immutable: no update endpoint exists and
submission reads the snapshot, not current Story/Scene/Canon values. There is no
new approval workflow engine or preview-plan table.

Repeated approval of the same user/plan/snapshot returns existing executions
without submitting again. Changed content under an already-approved plan ID
returns 409. A database uniqueness constraint protects user/plan/panel identity,
and PostgreSQL parent-row locking serializes concurrent approvals. These are
local replay protections, not an unsupported claim of IG-side idempotency.

M4B chooses four independent single-image submissions. IG has panel-grid
vocabulary, but this milestone does not optimize composite execution. The
StoryboardPlan is unchanged and describes four ordered intents, not four mandatory
provider calls. Future composite execution can associate multiple panels with a
shared external reference.

## API

All routes are prefixed with `/api` and require the existing IS-derived session.
Ownership checks return 404 for another user's Story, execution, or artifact.

| Method | Route | Behavior |
| --- | --- | --- |
| POST | `/stories/{story_id}/scenes/{scene_id}/storyboard/four-panel/execute` | Approve snapshot and attempt four submissions |
| GET | `/media/executions/{execution_id}` | Read durable execution without polling |
| POST | `/media/executions/{execution_id}/sync` | Poll existing external reference and persist status/result |
| GET | `/stories/{story_id}/media/executions` | List owned Story executions |
| GET | `/stories/{story_id}/artifacts` | List owned Story artifacts |
| GET | `/media/artifacts/{artifact_id}` | Read owned artifact metadata |

Execute accepts `{"approved": true, "plan": <M4A StoryboardPlan>}`. Missing/false
approval is rejected. The client submits the reviewed plan itself; the server
never silently rebuilds it from mutable authoring state. Approved custom prompts
are allowed, while Story/Scene relationships and Character/Outfit/Place references
are checked. Artifact references remain opaque until a verified resolver exists.

A 201 response means durable execution records exist, **not that media generation
succeeded**. Inspect all four `status` and `error_message` fields. In today's
unconfigured/live-disabled IG adapter, all four records fail clearly without HTTP.
Missing resources return 404, invalid approval/plan returns 422, and conflicting
plan replay returns 409. There is no frontend change.

## Synchronization and failure handling

Provider-neutral states are pending, submitted, running, completed, and failed.
Sync is request-driven; no workers, scheduler, queues, webhooks, or polling loop
are added. PostgreSQL row locks serialize sync of one execution. Completion and
Artifact creation commit atomically; terminal-state checks and execution/reference
uniqueness prevent duplicate artifacts on repeated refreshes.

A failed submission or remote failure produces no successful Artifact. Poll or
result-read transport failures retain the external ID and prior state so a later
sync can retry. Unknown upstream states and invalid/non-image results are errors,
not successful completion. Public/persisted diagnostics exclude raw upstream
response bodies and credentials.

A durable attempt marker is written before submission. Interrupted pending rows
without an external ID require manual reconciliation and are never automatically
resubmitted. A timeout may mean the remote service accepted the request even
though Sandcastle has no ID: do not approve another plan as an automatic retry.
IG-side idempotency/correlation lookup is needed for safe automated recovery.

## Artifact representation

`Artifact` stores local identity/ownership, Story/Scene/execution IDs, image/generated
type/source, an external reference, optional real external Artifact ID, retrieval
reference, MIME type, metadata, and creation timestamp. It is neither a filename
nor image storage. No media bytes are downloaded by sync or written to PostgreSQL.
Inline data URIs and local-file result references are rejected.

For the current generation response, `external_reference` is the IG **image request
ID**. `external_artifact_id` remains null because image read responses do not
expose that association. `retrieval_reference` points to the authenticated image
content endpoint; it is not a public URL, a signed download URL, or a byte proxy.
IG does have separate Artifact endpoints, but this adapter does not invent a link
between those objects and the image request result.

## Inspected IG contract and live blockers

Read-only inspection used the local IG working tree with HEAD `b369c9d` and
pre-existing local modifications; this is not a verified deployed contract. Files inspected include
`app/api/media.py`, `app/media/schemas.py`, `app/media/service.py`,
`app/api/images.py`, `app/images/service.py`, `app/auth/dependencies.py`,
`app/tenancy/dependencies.py`, and `app/api/artifacts.py`. No IG file was modified
or imported into Sandcastle.

The adapter maps the current image contract:

- `POST /v2/media/generations`: image/easy/single, prompt in `intent.description`,
  standard quality, count 1, single layout, and supported aspect ratio.
- Submission returns `{media_type, request_id, status}`; there is no Job ID.
- `GET /v1/images/{request_id}` returns image metadata/status. `generating` maps
  to running; completed and failed map directly. No provider/job state leaks out.
- `GET /v1/images/{request_id}/content` is recorded as the retrieval locator;
  sync does not fetch bytes or guess a storage URL.

Textual Character/Outfit/Place references are already expanded into the approved
prompt and retained in the snapshot; they are not passed as IG Artifact IDs.
Uploaded/generated artifact references are currently rejected rather than ignored:
a verified, owner-scoped resolver is needed to convert opaque references to actual
IG Artifact IDs. `9:16` and other unsupported aspect ratios are rejected rather
than silently coerced. Provider/model fields remain below the boundary.

**Live execution is deliberately blocked.** Current IG authentication uses the
`ig_session` browser cookie and hostname-based tenant membership. No safe
service-caller mechanism was found. Setting `IG_BASE_URL` alone or inventing
`IG_SERVICE_TOKEN` does not enable anything. The adapter permits only an explicit
in-process `httpx.MockTransport` for contract tests; no live transport is installed.
It never logs in, stores a password, forwards browser cookies, or bypasses auth.

Required change: Add documented service-caller authentication and authorized actor delegation.
Application: IG
Reason: Sandcastle must call IG as a service while the IS user remains the actor.
Expected contract: Validate a scoped service credential for Sandcastle, authorize
its tenant and delegated IS subject, and apply the same ownership checks to
submission, status, result, and content access. Document token audience/scopes,
actor/tenant mapping, and credential lifecycle. Browser cookies are not a substitute.

Required change: Repair the database-session argument in media submission.
Application: IG
Reason: The inspected `app/media/service.py` calls `submit_image_generation`
without the `db` argument required by `app/images/service.py`.
Expected contract: An authenticated valid `POST /v2/media/generations` durably
creates a request/job and returns its documented 202 image request response.
This is a source-level mismatch; no live request was made to verify deployment state.

For future automated retry/reference reuse, IG should also document idempotent
submission or correlation lookup and expose the generated image's Artifact ID.
Neither is fabricated by this adapter.

M5 video remains blocked on IG video capability. Uploaded artifacts, refinement,
lineage APIs, approval editing, composite optimization, queues, Axtor, and workflow
engines are deferred. No deployment or infrastructure modification is included.

## Validation

From `backend/`, normal tests need no IG configuration or running IG server:

```sh
.venv/bin/python -B -m unittest discover -s tests -p test_media_execution.py -v
.venv/bin/python -B -m unittest discover -s tests -p test_ig_client.py -v
.venv/bin/python -B -m unittest discover -s tests -v
```

Migration tests use temporary SQLite databases for upgrade/downgrade/model checks
and compile the entire migration history as PostgreSQL SQL. No configured live
database is migrated. Live IG testing is intentionally unavailable until the auth
and submission dependencies are resolved; normal tests use fakes and mock HTTP.
